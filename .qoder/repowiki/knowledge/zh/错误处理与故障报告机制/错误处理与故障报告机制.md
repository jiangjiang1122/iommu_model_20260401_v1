该 RISC-V IOMMU SystemC 性能模型采用**混合式错误处理策略**，结合了 C++ 标准异常、SystemC 运行时报告以及硬件规范定义的故障队列（Fault Queue）机制。由于是性能模型而非功能验证模型，其核心逻辑倾向于使用断言（assert）来捕获设计违规，而将符合规范的硬件错误通过数据结构传递。

### 1. 核心错误处理机制

*   **C++ 标准异常 (`std::runtime_error`)**:
    *   **应用场景**: 主要用于配置加载和初始化阶段。例如，在 `iommu/cache_src/common/json_config.cpp` 中，如果无法打开配置文件，会抛出 `std::runtime_error`。
    *   **资源保护**: 在缓存底层访问逻辑中（`cache_base.h`），使用了 `try-catch` 块来确保 RAM 端口锁（`release_ram_port`）在发生异常时能被正确释放，防止死锁。

*   **SystemC 运行时报告 (`SC_REPORT_ERROR`)**:
    *   **应用场景**: 用于检测 SystemC 仿真环境的使用违规。例如，在 `CacheSubsystem::push_fifo` 中，如果检测到调用者不在有效的 SystemC 进程上下文中，会触发 `SC_REPORT_ERROR` 并终止当前操作。

*   **断言 (`assert` / `sc_assert`)**:
    *   **应用场景**: 广泛用于内部状态一致性检查。在缓存替换策略（PLRU/SRRIP）、索引计算和集合访问中，大量使用 `assert` 来确保索引不越界、位宽合法等。这表明开发者将此类错误视为“不可恢复的设计缺陷”而非“运行时可处理错误”。

*   **硬件故障队列 (Fault Queue)**:
    *   **应用场景**: 模拟 RISC-V IOMMU 规范定义的硬件错误行为。当地址翻译过程中发生页表访问错误、权限违例或数据损坏时，模型不会抛出 C++ 异常，而是调用 `report_fault` 函数。
    *   **实现细节**: `report_fault` (在 `iommu_faults.cc` 中) 会根据错误原因（Cause Code，如 257-DDT load access fault）构建 `fault_rec_t` 结构体，并将其写入内存中的故障队列。如果队列满或写入失败，会设置相应的 CSR 寄存器位（如 `fqof`, `fqmf`）并触发中断。

### 3. 开发约定与建议

1.  **区分“模型错误”与“硬件错误”**:
    *   如果是模型实现本身的 Bug（如数组越界、空指针解引用），请使用 `assert`。
    *   如果是模拟硬件行为的错误（如页表项无效、权限不足），请调用 `report_fault` 并返回相应的错误状态码，**严禁**在此类路径抛出 C++ 异常，以免破坏 SystemC 仿真的稳定性。

2.  **资源安全性**:
    *   在持有共享资源（如 FIFO 写锁、RAM 端口）执行复杂逻辑时，必须使用 `try-catch` 或等效的守卫机制确保资源被释放。

3.  **配置与初始化**:
    *   在系统启动阶段的配置解析中，鼓励使用 `std::runtime_error` 快速失败（Fail-fast），以便开发者尽早发现配置错误。

4.  **避免静默失败**:
    *   对于缓冲区满等可预期的运行时状态（如 `DedupBuffer`），应通过返回值或状态标志通知调用者，并辅以 `std::cout` 日志记录，而不是直接崩溃。
